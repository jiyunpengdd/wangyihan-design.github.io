在硬件研发部门待过的人大概都有这个体感：一天里真正画图、写文档的时间不多，剩下的大半在找人。找谁批，找谁要数，找谁确认这个日期还能不能改。

RuiMate 要解决的是这一段，不是再造一个项目管理系统。

## 它不是聊天框，是一个能动手的同事

原型里十三个模块都是真能点的：任务、连接器、定时任务、记忆、项目库、组合仪表盘、交付物、变更与审批、审计日志、IPD 阶段门、知识库、工具集。左边那个输入框只是入口，干活的东西在右边。

用户进来第一件事不是说「你好」，是直接说事：结构冻结要推后两周，帮我走变更。

## 先给结论，再给依据

Agent 最容易犯的错是把过程当答案。用户问能不能推后两周，回一屏「我正在分析…」是最没用的。所以回答的结构是定死的：小标题、表格、提示条、快捷按钮，执行详情折叠到最后。

表格只有四行：变更对象、计划调整、受影响任务、影响评估。看完这四行，用户就该知道这件事能不能做、值不值得做。下面那条红字提示才是关键信息，它说的是规则，不是建议。

## 有些事不能让它自己决定

T03 是受控任务，发布之后不能直接改计划日期。这句话不写在帮助文档里，是 PLM 里的规则。Agent 得把它查出来、说出来，然后把动作停在「发起变更」这个按钮上。

这是整个设计里最重要的一条约束。Agent 可以查、可以算、可以催、可以起草，但不能替人签字。受控任务的变更必须由多级父任务负责人逐级审批，原型里这条做了硬拦截：绕过变更直接改日期的入口根本不给，不是灰掉，是不存在。

一个 Agent 产品好不好用，用户信不信它，往往就卡在这里。它越是能动手，边界越要说清楚。

## 规范不是给设计师看的，是给 Agent 看的

十三个模块如果各自长各的样，用户第一眼就不信这是同一个产品。所以先把一套东西定死：19 个 Token、26 个图标、49 个组件。

<Figure
  src={designSystem}
  alt="RuiMate 设计规范首页，左侧是十一个章节的目录，右侧是提取方式与可信度说明表，以及设计原则的三栏卡片"
  caption="规范文档里每个颜色、圆角、字号，都能在原型里找到同源代码。"
/>

图标全部 1px 线性描边，颜色永远继承文字色，不单独上色。强调色只有一个 #2f6bff 和它的浅底 #eaf1ff，语义色只用于状态。卡片是 1px 边、14px 圆角、3% 透明度的一层阴影，不靠投影分层。这些不是审美偏好，是为了让「哪个是主操作、哪个是提示、哪个是危险」在任何一页都读得出来。

规范文档不是重新画的，是从原型里机械抽出来的：样式表逐字内联，Token 从 `:root` 解析，图标从注册表取，组件 DOM 用无头浏览器抓真实节点。所以改视觉只能改原型再重新生成，不能在文档里打补丁，否则两份会分叉。

## 阶段门不是甘特图

IPD 的阶段门很容易被做成一条时间轴，看着整齐，但回答不了「现在能不能进下一阶段」。原型里每个阶段是一列：计划时间、负责人、交付物清单，底下是准入检查。

## 它得能碰到真东西

Agent 再聪明，碰不到 PLM 就是个玩具。连接器这一页本质上是一张权限清单：InTePLM+ 能读全部项目、写任务、变更单和交付物链接；企业微信发催办卡片；PDM 文档库做版本比对；钉钉和飞书做备用通道。

## 变更要走完，不能停在「已发起」

发起变更只是开头。变更单有三个状态：审批中、已通过、已驳回。通过之后自动生成基线变更记录，并且把下游的 T04 BOM 发布、T10 SOP 评审一起顺延。被驳回的那条写的是「需补充影响分析后重提」，不是简单一句失败。

<Figure
  src={changeFlow}
  alt="变更与审批页面，顶部三个统计卡分别是审批中一单、已通过一单、已驳回一单，下方变更单列表有三条记录，底部是变更影响提示与受控规则入口"
  caption="驳回也要说清楚缺什么，不然用户只能重开一单再试一次。"
/>

所有动作都写进审计日志。谁在什么时候让 Agent 做了什么，事后能查。
